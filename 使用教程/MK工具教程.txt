【近期版本变更】
  2.14.1 修「挂载咔咔数据目录」一执行就报 `KAKAKE_DATA: readonly variable` 并退出
         （重建时对 readonly 变量赋值导致）；改为命令行参数传值，文案也去掉 ENOENT 术语。
  2.14.0 NapCat Docker 容器详情新增「挂载咔咔数据目录（治本）」：手动装的容器发视频/图片
         报 ENOENT 时，一键重建容器补挂载（保留镜像/端口/环境/登录态），并修容器内 /root 权限。
  2.13.1 修复手动装的 Docker NapCat 识别不到：现在会自动发现 docker 里镜像含 napcat 的
         容器（无论是不是 mk 装的），菜单标题、[11] 容器列表、[9] 登录密钥、[3]/[4] 启停
         都能覆盖；手动容器标注「手动安装」，卸载时不会连坐删除（只删 mk 自己装的）。
  2.13.0 NapCat Docker 版补全：拉镜像前可选 Docker Hub 加速源（直连 / docker.1ms.run /
         docker.xuanyuan.me / docker.mybacc.com / dytt.online / lispy.org）；
         容器列表 [11] 升级为子菜单，选中单个容器可单独启动/停止/重启/看密钥/看日志/删除。
  2.12.0 NapCat 安装新增「Docker 版」：NapCat 不支持单框架多开，要一台机器跑多个 QQ
         只能每个账号一个容器。安装时可选 Docker / Shell，Docker 版按 QQ 号建容器、
         自动分配端口、挂载咔咔数据目录（发视频/图片不再 ENOENT），可重复安装实现多开。
  2.11.6 native 模式启动 SnowLuma 时自动拉起所有 QQ 账号（像 docker 那样一键全套）；
         修主账号 QQ 启动命令也缺 GPU 三参数（--in-process-gpu 等）。
  2.11.5 修 native 模式 QQ 启动即崩：无头服务器上 Chromium 仍会尝试拉 GPU 进程并 FATAL 退出，
         加 --disable-gpu-sandbox --in-process-gpu --use-gl=swiftshader 三个参数根治。
  2.11.4 修「挂载有了但读不到」：挂载只覆盖最后一层，它上面的 /root 是镜像自带的（700），
         必须进容器改。建容器时自动补一次；[7] 新增 [3] 修容器内父目录；[8] 逐层排查两侧权限
  2.11.3 [20] 新增「挂没挂上」状态显示：菜单顶部直接告诉你清单里有几个还没挂进正在跑的
         容器；[8] 验证会先判挂载是否生效，区分「没重建容器」与「权限不够」两种原因
  2.11.2 修复 [20] 菜单「修权限」一按就把 mk 顶出去的问题（set -u 下无参调用
         snowluma_mounts_fix_perms 触发 $1 unbound variable）；新增参数的函数一律改用 ${1:-}
  2.11.1 [20] 挂载菜单会自动探测 kakake 目录（认 package.json / data），[2] 直接回车即可
         采用；已挂目录没覆盖到 kakake 时给出提醒
  2.11.0 SnowLuma 新增「容器额外挂载」（菜单 [3] → [20]）：把宿主目录按相同绝对路径挂进
         Docker 容器（默认只读），解决 Docker 模式下咔咔珂发图片/视频报 EACCES、
         合并转发被协议端拒（retcode=100）的问题；附带权限修复与容器内读验证
  2.10.0 SnowLuma 多账号多开支持「直接安装(native)」模式（菜单 [3] → [19]）：
         每个账号独占一个宿主机 HOME，由 mk 逐个拉起/停止，可单独启停单个账号不波及其它
  2.9.0  新增主菜单 [13] 性能体检：CPU 型号/单核跑分、宿主机超售 st、cgroup 配额、
         /tmp 是否内存盘、磁盘写速、Node/sharp/libvips、内存 swap，并给出汇总评定
  2.8.0  SnowLuma 新增 Docker 多账号多开（菜单 [3] → [19]）：一个容器跑多个 QQ，
         靠 SNOWLUMA_EXTRA_QQ_HOMES + 每账号独立 HOME 卷，增删后重建容器不丢登录态

【这是干什么的】
mk 是一键管理脚本，交互菜单里可以：
  · 装/管宝塔
  · 装/启停 NapCat（QQ）
  · 装/启停 SnowLuma（Docker 或直接安装）、装兼容 QQ、多账号多开
  · 性能体检：CPU 型号与单核跑分、宿主机超售、cgroup 配额、磁盘写速、内存 swap
  · 装/启停咔咔珂、装 Node、构建 Web UI
  · 查端口占用、构建 MK 插件源码、NapCat 实验魔改、开机自启
  · 检测/安装中文字体包（软件源、国内代理镜像、本地文件）

【适用环境】
  · Linux 服务器（需 bash；多数操作要 root / sudo）→ 全部功能可用
  · Termux（安卓手机，2.6.0 起支持）→ 免 root，但只有部分功能可用，见下方说明
  · 不是 Windows 本机用的；Windows 请用仓库里的 start.bat 起咔咔
  · 咔咔支持两种形态（mk 会自动识别；安装时可二选一）：
      源码版：下载 kakake.zip，含 scripts/bootstrap.mjs，启动前可构建 Web，可用 mk 私有/系统 Node
      便携版：下载 kakake-linux-x64.zip，含 runtime/bin/node + packages/server/main.mjs，无需再装 Node、无需构建 Web
        解压后统一装到 ~/kakake（zip 内目录名可以是 kakake 或 kakake-linux-x64）
        手动部署时把 kakake-linux-x64 目录内容放到 ~/kakake 亦可
        便携版仅限 x86_64 + glibc，安卓（arm64 + bionic）不可用，手机上只能装源码版

【Termux（安卓手机）差异一览】
  可用：[4] 咔咔操作、[5] 端口验证、[6] 构建 MK 源码、[9] 开机自启、[8] 卸载 mk、[10] 字体包（仅检测）
  拦截：[1] 宝塔、[2] NapCat、[3] snowLuma、[7] 实验功能、[12] Docker
        （这些依赖 root / systemd / X11 桌面，手机上没有；点进去会说明原因并返回）
        [10] 字体包在手机上改为「仅检测不安装」：读 /system/fonts、$PREFIX/share/fonts
             等目录，用 fc-list（装了 fontconfig 时）报告是否已有中文字体；不写系统目录、
             不下载/安装字体、也不需要 root。安装字体仍请在电脑/服务器上做。
  路径：安装目录改挂到 $PREFIX 下，不写 /usr/local 与 /var/log
          脚本本体  $PREFIX/lib/mk-tools/mk
          全局命令  $PREFIX/bin/mk
          日志目录  $PREFIX/var/log/mk-tools/
  权限：无需 root，也不要加 sudo（Termux 里本来就没有）
  Node：走 pkg install nodejs-lts（当前为 22.x），而不是下载官方二进制
  自启：安卓没有 systemd，改用 Termux:Boot，脚本写在 ~/.termux/boot/20-kakake.sh
  临时目录：安卓没有 /tmp，统一走 $PREFIX/tmp
  端口查询：手机上常缺 ss / netstat，[5] 端口验证会自动改读 /proc/net/tcp
  手机完整部署步骤见《04-Termux 安卓手机 使用教程.txt》

--------------------------------------------------------------------------------
一、安装 / 更新 mk
--------------------------------------------------------------------------------
把仓库里的 mk 文件拷到服务器后（或用已有路径）：

  # 首次安装或强制更新到系统（需要 root）
  sudo bash mk
  # 或
  sudo bash mk --install

  # Termux（安卓手机）：不要加 sudo
  bash mk

安装完成后（Linux）：
  · 脚本本体：/usr/local/lib/mk-tools/mk
  · 全局命令：mk  （软链到 /usr/local/bin/mk）
  · 日志目录：/var/log/mk-tools/

日常打开菜单（已装过全局命令时）：

  sudo mk
  # 或
  mk

常用参数：
  mk --version / -v     查看版本
  mk --help / -h        用法说明
  mk --check / -c       语法检查
  mk --install / -i     强制重装/更新
  mk --uninstall / -u   卸载 mk 工具本身（不自动卸 NapCat/咔咔，见菜单）

三、推荐上手流程（服务器上从零到可聊）
--------------------------------------------------------------------------------
1) sudo bash mk 安装 mk（若尚未安装）
2) 主菜单 → [2] NapCat → [2] 安装框架（单账号选 Shell；要多开选 Docker，每账号一个容器）
3) NapCat 装完 → [3] 启动 → [9] 看面板登录密钥，浏览器进 NapCat WebUI 扫码
4) 主菜单 → [4] 咔咔操作
     · 菜单会显示「安装形态: 源码版 / 便携版」
     · 便携版：Node 显示「便携内置」，可直接 [5] 启动；无需 [3] 装 Node、无需 [10] 构建 Web
     · 源码版：若提示没有 Node，可 [3] 安装 Node.js（mk 私有一份）
       若本机已有全局 Node，菜单会显示「系统全局」，一般可直接用，不必再装
     · [2] 安装咔咔 → 会询问源码版 / 便携版 → [5] 启动咔咔
       （源码版未构建 Web 时启动会先构建；便携版可直接启动）
     · 重装仍保留 data/ 与 plugins/
     · [9] 查看登录密钥 → 浏览器打开控制台（默认端口 8787）
5) 按《连接教程.txt》把 NapCat / SnowLuma 与咔咔连上（推荐本机反向 WS）
6) 端口冲突：主菜单 → [5] 端口验证
7) 中文方块/截图乱码：主菜单 → [10] 字体包操作 → 先 [2] 扫描，再按网络情况安装

四、NapCat 菜单（主菜单 [2]）
--------------------------------------------------------------------------------
  [2] 安装框架           可选 Docker 安装 / Shell 直接安装
  [3] 启动框架
  [4] 停止框架
  [5] 重启框架
  [6] 配置框架           含网络配置等
  [7] 卸载框架
  [8] 查看日志
  [9] 查看 NapCat 面板登录密钥
  [10] 查看安装进度      （仅 Shell 安装进行中时有用）
  [11] Docker 容器列表   （仅装了 Docker 版时显示；选容器可单独启停/删除，2.13.0 起）

说明：
  · Docker 版（2.12.0 起）：NapCat 不支持单框架多开，要一台机器跑多个 QQ 只能
    每个账号一个容器。[2] 安装 → 选 Docker 安装 → 输入 QQ 号即建一个容器；
    再装一次就是再加一个容器（多开）。自动分配端口、自动挂载咔咔数据目录
    （解决发视频/图片报 ENOENT 的问题）、数据卷持久化登录态。
  · Docker 版拉镜像前可选加速源（2.13.0 起）：国内拉不动 Docker Hub 时选
    docker.1ms.run / docker.xuanyuan.me 等镜像加速前缀，默认直连。
  · [11] 容器列表（2.13.0 起）：选中单个容器可单独启动/停止/重启/看密钥/看日志/删除，
    不影响其它容器；顶部菜单 [3] 启动框架仍是「一键启动全部容器」。
  · 容器详情里的「挂载咔咔数据目录」（2.14.0 起）：手动装的容器发视频/图片失败时，
    进 [11] → 选容器 → [8]，一键重建容器补挂载咔咔数据目录
    （保留镜像/端口/环境/登录态），并自动修容器内权限。
  · 自动识别手动容器（2.13.1 起）：不管容器是 mk 装的还是手动 `docker run` 出来的，
    只要镜像名含 napcat 就会被自动识别，菜单标题/容器列表/登录密钥/启停都能覆盖；
    手动容器会标注「手动安装」，卸载框架时不会连坐删除（只删 mk 自己装的）。
  · Shell 版：安装脚本地址由 mk 内置（经代理拉取 NapCat-Installer）
  · 指定版本时还会按所选镜像代理拉取 NapCat.Shell.zip
  · 默认安装路径常见为 ~/Napcat 或 /opt/QQ（以安装脚本与本机检测为准）

四-B、snowLuma 菜单（主菜单 [3]）
--------------------------------------------------------------------------------
  [2] 安装 SnowLuma       可选 Docker 安装 / 直接安装（解压发行包）
  [3] 卸载 SnowLuma
  [4] 安装 QQ             按架构与已装 SnowLuma 版本列出兼容下载地址并可安装
  [5] 启动 QQ             常规模式会同时拉起 Xvfb+VNC+noVNC 扫码桌面
  [6] 停止 QQ             常规模式一并停扫码桌面
  [7] 彻底杀死 QQ         强杀 /opt/QQ 进程树并短时压制自动拉起（不关 VNC）
  [8] 卸载 QQ             卸宿主 linuxqq（/opt/QQ）
  [9] 启动 SnowLuma
  [10] 停止 SnowLuma
  [11] 重启 SnowLuma
  [12] 查看日志
  [13] 查看 WebUI 登录信息
  [14] 查看扫码地址       noVNC / VNC 端口与密码
  [15] 仅启动远程查看
  [16] 仅停止远程查看     不影响 QQ
  [17] 配置扫码端口/密码  noVNC/VNC 均可改（默认 6081/5900）
  [18] WebUI 监听地址/外部访问  直接安装版 WebUI 只绑 127.0.0.1 时，一键开放外部访问
  [19] 多账号（多开）         一个 SnowLuma 跑多个 QQ 账号（Docker / 直接安装都支持）
  [20] 容器挂载目录         让容器读到宿主机目录（Docker 模式发媒体失败时用，2.11.0 起）

说明：
  · Docker：镜像 motricseven7/snowluma:latest，内置 QQ + noVNC（默认 6081）+ WebUI（5099）
    mk 起容器时已带 SNOWLUMA_WEBUI_HOST=0.0.0.0（WebUI 对外）、SNOWLUMA_QQ_FLAGS（关 GPU 防泄漏）、
    --ulimit nofile 抬高句柄上限；数据卷 snowluma-data 挂到 /app/data（SnowLuma 配置/onebot.json/
    runtime.json 都在这），另两卷 /app/.config、/app/.local/share 存 QQ 客户端配置与登录态
  · 多账号/多开（菜单 [19]；Docker 模式 2.8.0 起，直接安装模式 2.10.0 起）：
      不需要多个容器，也不需要多套虚拟屏。Linux QQ 的单实例锁落在
      $HOME/.config/QQ/SingletonLock，所以多开的唯一硬性条件是「每个 QQ 独占一个 HOME」，
      两种安装方式都一样。SnowLuma 侧零配置：HookManager 遍历所有 QQ 主进程逐个注入
      （hook 的 socket 按 PID 命名），每个 UIN 自动起一个 OneBotInstance，
      WebUI 自动列出所有 UIN。
      - 主账号固定占第 1 个，额外账号从 qq-acct2 起编号；移除后空出的编号会被复用
      - 所有 QQ 窗口共用同一个 Xvfb 桌面，一个 noVNC 就能逐个切换窗口扫码
      - 每个 QQ 进程约吃 300-500MB 内存
      - 账号清单记录在 /var/log/mk-tools/snowluma-accounts，卸 SnowLuma 时会一并清理

      Docker 模式（账号由镜像内的 supervisor 托管）：
      - mk 往容器注入 SNOWLUMA_EXTRA_QQ_HOMES=/app/qq-acct2,/app/qq-acct3，并给每个 HOME
        挂一个独立数据卷；supervisor 为每个 HOME 生成一个 program（qq-extra-1、qq-extra-2…）
      - 添加/移除账号需要重建容器才生效；mk 只删容器、不动数据卷，已有账号登录态不丢
      - 多开时共享内存自动从 1g 提到 2g

      直接安装(native) 模式（没有 supervisor，由 mk 自己逐个拉起）：
      - 账号 HOME 落在宿主机 /opt/snowluma-qq-acct/qq-acctN（刻意不放 /opt/SnowLuma，
        那个目录重装 SnowLuma 时会被整目录备份走）
      - 每个账号一个独立 PID 文件 snowluma-qq-<账号名>.pid；即使 PID 文件丢了，
        也能靠读 /proc/<pid>/environ 里的 HOME 把进程认回来
      - 菜单 [19] 的 [5]/[6] 可单独启动/停止某一个账号，不会波及其它账号
      - 注意两点：① 没有 supervisor，QQ 崩了不会自动重启；
        ② 主菜单的 [6] 停止 QQ / [7] 彻底杀死 QQ 是杀全部账号，只停某一个请走 [19]
  · 容器额外挂载（菜单 [20]，2.11.0 起；只有 Docker 模式需要）：
      症状：Docker 模式下咔咔珂/插件发图片、发视频失败，日志里出现 realpath EACCES；
            或者合并转发整条被拒（retcode=100）。
      原因：咔咔珂发媒体时给协议端的只是一个本地路径字符串（file:///root/kakake/data/…），
            真正去读盘上传的是「容器里的 SnowLuma」。宿主机路径在容器自己的文件系统里
            根本不存在，于是读不到；合并转发里只要含本地路径，整条消息会被一并拒绝。
      解法：把宿主机目录以「左右完全相同的绝对路径」挂进容器，例如
              -v /root/kakake:/root/kakake
            路径一个字都不能差，否则咔咔珂传进来的字符串在容器里依旧对不上。
      用法：菜单 [3] → [20]
              [2] 添加     填宿主机绝对路径（会校验存在、拒绝相对路径、/ 和含空格路径）
                          2.11.1 起会自动探测 kakake 目录：认目录里有 package.json 或
                          data 的那个，直接回车就采用它（推荐，一次覆盖 data 与
                          plugins_two）；探测不到才需要手填
                          已挂的目录没覆盖到 kakake 时，菜单顶部会提醒一句
              [3] 移除     从清单里删掉（重建容器后才不再挂载）
              [4] 查看     列出当前清单及对应的 docker 参数
              [5] 切换     只读 / 可写（默认只读；协议端只需要读，只读更安全）
              [6] 重建     重建容器让挂载生效（会先自动修一次权限）
              [7] 修权限   [1] 宿主机目录 a+rX + 父目录 o+x（快，先试）
                          [2] 宿主机递归 a+rX（文件 600 时才需要，慢）
                          [3] 容器内父目录 o+x（挂载已生效却读不到时用这个，不用重建）
              [8] 验证     在容器里以 snowluma 用户实读一个文件（不要用 root 验，会假阳性）
      正确顺序：[2] 添加 → [7] 修权限 → [6] 重建容器 → [8] 验证
              ⚠ 顺序别乱：挂载是「建容器时」写进去的，**没重建容器就 [8] 一定读不到**。
                2.11.3 起菜单顶部会直接显示「其中 N 个还没挂进正在跑的容器」，
                [8] 也会先判挂载是否生效再判权限，不会再把「没重建」误报成「权限不够」。
      建议挂的目录：
              /root/kakake            最省事，一次覆盖 data / plugins / plugins_two
              /root/kakake/data       只想给协议端读数据目录时
              /root/kakake/plugins_two  每个账号一份插件数据，多账号时可能各自有目录
              （按你实际的咔咔珂安装目录填，用 [4] 能看到宿主机上目录是否还在）
      三个常见坑：
        ① /root 默认 700，容器里的 snowluma(uid 1000) 连目录都进不去 ——
           用 [7] 补 o+x（只给执行位，不给读位，不会泄露目录列表）
        ② 手动 docker run 加的 -v 会在 mk 重建容器时丢掉 —— 一律走 [20] 登记，
           mk 建容器时会自动带上，重建不丢
        ③ 验证必须用 [8]（容器里是 snowluma 用户）；在宿主机或用 root 验都看不出问题
      ⚠ 最容易搞混的一点：权限有「两侧」，而挂载只覆盖最后一层。
        挂 -v /root/kakake:/root/kakake 时，被换掉的只有 /root/kakake 这一层；
        它上面的 /root 是**容器镜像自带**的（默认 700 root:root），
        在宿主机上执行 chmod o+x /root 改的是宿主机的 /root，**跟容器里那层毫无关系**。
        这就是「挂载已生效 ✓ 但容器读不到 ✗」的典型成因。
      两侧分别怎么修（2.11.4 起）：
        · 容器内父目录 → [7] 选 [3]（docker exec -u 0 chmod o+x），**不用重建容器**；
          但改的是容器可写层，以后每次 [6] 重建都会丢 —— mk 建容器时会自动补一次
        · 宿主机目录本身 / 宿主机父目录 → [7] 选 [1]（或 [2] 递归），然后 [6] 重建
      [8] 报「读不到」时的两种原因（2.11.3 起会分开提示，别再猜）：
        · 「还没生效：容器里没有这个挂载」→ 挂载没写进容器，**去 [6] 重建容器**即可
        · 「容器读不到 ✗」→ 挂载有了但进不去；2.11.4 起 [8] 会**逐层**列出容器视角的
          父目录权限并标出卡在哪一层，按提示回 [7] 选对应的修法
      [7] 的两种修法怎么选：
        · [1] 只修目录本身 + 补父目录 o+x —— 先试这个，快，不改文件权限
        · [2] 递归 a+rX —— 文件是 600 时才需要；大目录（含 node_modules）会慢，
          且会把 kakake 下所有文件（含 data/auth-key.json）变成全局可读，谨慎使用
      记录位置：/var/log/mk-tools/snowluma-mounts（一行一个绝对路径）
                只读开关 /var/log/mk-tools/snowluma-mounts-ro（1=只读，0=可写）
      影响面：只重建容器，不碰任何数据卷，QQ 登录态与咔咔珂数据都不受影响；
              咔咔珂本身不用重启。卸载 SnowLuma 时这两个文件会一并清掉。
      直接安装(native) 模式本来就和咔咔珂在同一文件系统，不需要挂载（菜单会提示）。
  · 直接安装：解压到 /opt/SnowLuma；「启动 QQ」会装并启动 Docker 同款扫码栈
    （Xvfb :99 + openbox/fluxbox + x11vnc + noVNC；默认端口 5900/6081）
  · 扫码密码（noVNC/VNC）：官方镜像会把 vncpasswd 这类公开示例值当作未设置并改用随机密码，
    所以 mk 装 Docker 时会自动生成一个随机强密码（形如 snow-xxxx）作为 VNC_PASSWD，并在 [13]
    登录信息里显示实际生效的密码；[13] 会直接从容器日志/启动日志抓 noVNC 与 WebUI(admin) 的真实
    密码显示，抓不到时给出 docker logs 查询命令。直接安装(native) 用 mk 自带 VNC，密码本地即生效
  · 端口可改：菜单 [17]，或编辑 /var/log/mk-tools/snowluma-vnc.env，也可
    export MK_SNOWLUMA_NOVNC_PORT=8081 MK_SNOWLUMA_VNC_PORT=5901
    （注意：Docker 模式端口/密码在建容器时固定，改完要「卸载→重装」容器才生效）
  · WebUI 外部访问（菜单 [18]，仅直接安装版需要）：某些版本 WebUI 只监听 127.0.0.1，直连服务器
    外部打不开。[18] 首选「改 SnowLuma 监听 0.0.0.0」——写入偏好后，mk 在启动 SnowLuma 时注入
    环境变量 SNOWLUMA_WEBUI_HOST（优先级高于 runtime.json），本体直接对外监听，干净不占额外端口；
    改完若在运行会问你是否立即重启生效。[3] 改回仅本机 127.0.0.1。万一某旧版本不认这个变量，
    [4] 提供 socat 兜底：在「本机IP:同端口」转发到 127.0.0.1（首次会自动装 socat 并放行防火墙）。
    Docker 模式已对外，无需此项。注意：WebUI 暴露到公网有风险，请设强密码并尽量只放行可信来源。
  · 扫码：浏览器打开 http://服务器IP:端口/ ，在 QQ 窗口扫码（不是完整 Linux 桌面）
  · 安装 QQ：优先读官网 rainbow（dldir1v6.qq.com 新域名），失败再试 GitHub 归档镜像
  · 旧 qqdl.gtimg.cn 通道仅作备用（不少网络已 404）
  · 与 NapCat 共用 /opt/QQ 时请注意互相启停，避免冲突

六-B、性能体检（主菜单 [13]，2.9.0 起）
--------------------------------------------------------------------------------
判断机器到底跑不跑得动咔咔珂 / SnowLuma / QQ。光看「几核几 G」不准——
云厂商超售、容器配额、/tmp 是不是内存盘、磁盘 IO 都会让标称配置大打折扣。

  [2] 一键全检        依次跑完下面全部，约 20-40 秒（Ctrl+C 可中断，前面的结果仍有效）
  [3] CPU 型号/主频/核数   lscpu；没有则回落到 /proc/cpuinfo
  [4] 宿主机超售           vmstat 采样 5 次看 st 列（偷走的时间），>5% 要警惕
  [5] cgroup 配额          读 cpu.max（v2）或 cfs_quota_us（v1），算出实际能吃几核
  [6] /tmp 是否内存盘      df -hT /tmp，tmpfs = 内存盘（写快但吃内存、重启清空）
  [7] 磁盘写入速度         写 200MB 实测；优先 oflag=direct 绕过缓存，不支持则降级
  [8] CPU 跑分             node 跑 3 亿次累加计时，最能直接反映单核算力
  [9] Node / sharp / libvips
  [10] 内存与 swap         free -h + swapon --show；没有 free 则读 /proc/meminfo

怎么看结果：
  · [8] CPU 跑分是横向对比最有用的一项：<1.5s 很快，1.5-3s 正常，3-6s 偏慢，>6s 很慢
    （含 node 启动开销，不同架构/Node 版本差异较大，只作粗参考）
  · [4] st 高 + [8] 跑分慢 → 宿主机超售，换机器最有效
  · [5] 配额只有 1-2 核 + [8] 跑分慢 → 容器被限了，找服务商加配额
  · [7] 写速低于 50MB/s → 磁盘 IO 差，插件安装/更新、日志写入都会卡

命令缺失时（精简镜像常见 lscpu/vmstat 不全、安卓基本都没有）会自动跳过该项并说明，
不会整套失败——能看几项看几项。磁盘写测试前会先查剩余空间，不足 400MB 直接跳过。

【体检结论】
一键全检跑完会在最后给一段汇总评定，把上面各项收拢成一句结论：

    单核算力 : 1415 ms（很快）        3 亿次累加耗时，含 node 启动开销
    可用核数 : 20（CPU 逻辑核）       容器里优先显示 cgroup 配额
    内存     : 16214 MB（约 15 GB）
    磁盘写速 : 282 MB/s
    宿主超售 : st 峰值 3%
    综合评级 : 游刃有余
    能跑什么 : 咔咔珂 + 2~3 个 QQ 都能跑
    主要瓶颈 : 无明显瓶颈

评级怎么定的：
  · 游刃有余  单核 <1.5s 且内存 ≥4GB      → 咔咔珂 + 2~3 个 QQ
  · 够用      单核 <3s   且内存 ≥2GB      → 咔咔珂 + 1 个 QQ
  · 勉强      单核 <6s   且内存 ≥1GB      → 够跑咔咔珂，加 QQ 会比较紧
  · 吃力      更慢或内存更小              → 建议换机器，或先只跑咔咔珂
  · 额外压档：CPU 够但内存 <2GB → 压到「勉强」；cgroup 配额 <2 核 → 压到「勉强（配额仅 N 核）」

主要瓶颈按「最该先解决」排序，只报最主要的一个：
  宿主机超售（st>5%）> 容器配额 <2 核 > 内存 <1GB > 单核 ≥3s > 磁盘 <50MB/s

没测到的项不参与判定，所以命令不全时结论会相应保守（例如缺 node 没跑分时，
只能按内存给结论，评级会带「未测跑分」字样），不会编数字也不会给错方向。
跑分数字只用来横向对比机器，别和网上其他基准直接比绝对值。
