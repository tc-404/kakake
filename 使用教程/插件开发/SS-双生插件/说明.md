# 双生插件（sssx-）开发手册

> **先看这一句**：双生插件 = **一份代码，同时能挂在两条协议上**：
> ① **OneBot11 / NapCat**（就是 `kakake-` 那条路）；② **QQ 官方机器人**（就是 `GF-` 那条路）。
>
> 咔咔珂**只负责「双路由」**：把同一个 `sssx-plugin-*` 目录同时装载到 OneBot 连接和官方机器人连接上，
> 各自独立 `plugin_init` / 数据目录 / 后台路由，**并且明确告诉你这一条事件来自哪条协议**。
>
> **怎么兼容两套事件结构、怎么把发送接口抹平——那是插件自己的事，框架不管。**
> 想偷懒的话：一个插件里写两份分支（按 `ctx.frameworkEnv.protocol` 分路）就行。
>
> 本手册只讲双生插件**独有的机制**。两套协议各自的事件字段与发送形态，分别去读：
> - OneBot 侧 → `前言.md`（`kakake-` 同款事件：`message` 段数组、`user_id` / `group_id`、`send_group_msg`）
> - 官方侧 → `GF-官方机器人/说明.md`（`event.content`、`group_openid`、`/v2/groups/{id}/messages`）

## 一、双生是什么、不是什么

|  | 双生插件（`sssx-`） | 普通 OneBot（`kakake-`） | 官方（`GF-`） |
| --- | --- | --- | --- |
| 能挂在 OneBot 连接上 | ✅ | ✅ | ❌ |
| 能挂在 QQ 官方连接上 | ✅ | ❌ | ✅ |
| 一份代码两边通用 | ✅（框架只铺路，兼容自己写） | — | — |
| 事件结构 | **两种都有**，按协议分路 | OB11 一种 | 官方一种 |
| 数据目录 | 按账号隔离（QQ 号 / AppID） | 按 QQ 号 | 按 AppID |

**不是什么**：
- **不是**「框架帮你把官方事件转成 OneBot 消息段」。事件是**原样透传**的，官方事件里没有 `message` 数组，OneBot 事件里没有 `content`。
- **不是**「一个插件实例同时收两条协议」。是**每个账号一份独立实例**：同一个插件在 OneBot 的 123456 账号上跑一份，在官方 AppID `1020xxxx` 上再跑一份，`plugin_init` 各调一次，数据各存各的。

## 二、目录与命名（硬规则）

1. 文件夹**必须以 `sssx-plugin-` 开头**，例如 `sssx-plugin-hello`。
   - 写成 `sssx-hello`、`SS-plugin-hello`、`ss-plugin-hello` 都**认不出来**：
     前者会被当普通目录忽略，后两个会被判成 KOOK 插件（`ss-plugin-`）。
2. 安装源统一放 `plugins/`；运行副本由框架复制到 `plugins_two/<账号键>/<插件目录名>/`。
3. 入口导出与其它插件**同名同签名**：`plugin_init` / `plugin_onevent` / `plugin_onmessage` / `plugin_cleanup`。
   ESM（`export`）和 CJS（`module.exports`）都支持。
4. 总开关写在 `data/sssx-plugins.json`；每条连接上的子开关写在 `data/connection-plugins.json`。
   两者都开，插件才会在那个账号下真正加载。

导入 zip 时框架按目录名 / 包名自动识别成双生插件，不需要手动选类型。

## 三、双路由：一个账号一份实例

```text
plugins/sssx-plugin-hello/            ← 安装源（你写的那一份）
        │  框架复制
        ├──► plugins_two/123456/sssx-plugin-hello/        ← OneBot 账号（QQ 号 123456）的运行副本
        └──► plugins_two/1020xxxx/sssx-plugin-hello/      ← 官方账号（AppID 1020xxxx）的运行副本

每条连接各自：plugin_init 一次 · 独立 dataPath · 独立 route · 独立内存状态
事件派发：哪条连接来的事件，就只发给那条连接账号下的那一份实例
```

**两个协议互不串台**：官方群里的消息不会跑到 OneBot 那份实例里去，反之亦然。

## 四、框架下发给插件的标识（重点）

这一节就是「咔咔珂到底给插件塞了什么」，写双生插件**只需要认这几项**。

### 4.1 首选：`ctx.frameworkEnv.protocol`

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| `ctx.frameworkEnv.protocol` | `'onebot'` \| `'qq_official'` | **判别协议用这个**，最直接、不会歧义 |
| `ctx.frameworkEnv.ob11Mode` | `'ws-server'` \| `'qq-official-ws'` \| `'qq-official-https'` | 更细：连的是哪种模式。OneBot 恒为 `'ws-server'`；官方按连接配置给 WebSocket / HTTPS |
| `ctx.frameworkEnv.connectionId` | 连接 ID | 同一条协议下区分不同连接 |
| `ctx.frameworkEnv.frameworkId` | `'kakake'` | 恒为 kakake，用于判断宿主 |
| `ctx.frameworkEnv.frameworkVersion` | 如 `'0.6.4'` | 宿主版本，做兼容判断用 |

`protocol` 在 `plugin_init` 里**也有值**（取该账号第一条已启用连接的类型）；
在事件回调里则按**这条事件本身**重算——事件带 `t` 字段判为官方，否则是 OneBot
（见 `src/plugin/sssx-plugin.manager.ts`）。两种读法结论一致，挑一个用就行。

### 4.2 事件对象上的标记

框架给每个事件对象补一个布尔标记，两种协议互不重叠：

| 标记 | 出现时机 |
| --- | --- |
| `event.onebot === true` | 这条事件来自 OneBot 连接 |
| `event.qq_official === true` | 这条事件来自 QQ 官方机器人连接 |

```js
if (event.qq_official) { /* 官方事件：event.t / event.content / event.author */ }
else if (event.onebot) { /* OB11 事件：event.post_type / event.message / event.user_id */ }
```

> 这两项和 `ctx.frameworkEnv.protocol` 是**同一个判断的两种读法**，挑一个用就行，
> 别写两套互相打架的分支。

### 4.3 ctx 上其它固定项

| 字段 | 值 / 含义 |
| --- | --- |
| `ctx.pluginName` | 插件目录名，如 `sssx-plugin-hello`（**带前缀**） |
| `ctx.pluginPath` | 运行副本目录（`plugins_two/<账号>/<插件名>`），**别往这里写数据**，重载会被覆盖 |
| `ctx.dataPath` | `data/<账号键>/<插件名>` —— 写数据只写这里 |
| `ctx.configPath` | `<dataPath>/config.json` |
| `ctx.adapterName` | `sssx_plugin_manager:<connectionId>:<插件名>`（插件初始化时是 `sssx_plugin_manager:<账号键>:<插件名>`） |
| `ctx.connectionId` | **仅事件回调中有值**；`plugin_init` 里可能是 `undefined` |
| `ctx.logger` | 插件日志器，分类为 `plugin`（进后台日志与 `log/` 文件） |
| `ctx.actions.call(action, params)` | 出站动作，**按连接类型自动分流**（见 §6） |
| `ctx.router` | 后台页面 / API 注册器，**与单协议插件完全一致** |
| `ctx.NapCatConfig` / `ctx.core` / `ctx.oneBot` | 与其它插件一致，无差异 |

账号键怎么来的：**OneBot → 机器人 QQ 号；官方 → AppID**。两个命名空间天然不冲突。

## 五、事件侧：这次事件是哪条协议

### 5.1 OneBot 侧（长这样）

```js
{
  post_type: 'message',          // message / notice / request / meta_event / action_result
  message_type: 'group',         // group / private
  sub_type: 'normal',
  message_id: 12345,
  user_id: 10001,                // QQ 号，是数字
  group_id: 888888,              // 群号，是数字
  raw_message: '你好',
  message: [ { type: 'text', data: { text: '你好' } } ],   // 消息段数组
  sender: { user_id: 10001, nickname: '张三', card: '', role: 'member' },
  self_id: 123456,
  onebot: true,                  // ← 框架补的标记
}
```

### 5.2 官方侧（长这样）

```js
{
  t: 'GROUP_AT_MESSAGE_CREATE',  // 事件名，也有 GROUP_MESSAGE_CREATE / C2C_MESSAGE_CREATE
  id: 'xxxx',                    // 被动回复要用它当 msg_id
  content: '你好',                // 纯文本字符串（不是数组），里面可能混着 @ 标记，见下
  group_openid: 'xxxx',          // 群 openid（32 位字符串，不是群号）
  author: {                      // 群里用 member_openid；单聊用 user_openid
    member_openid: 'xxxx',
    // 实测（log/2026-10-13.log）author 里通常还带这几个，能省不少事：
    username: '张三',            // 昵称，平台直接给的（不保证一定有，做好为空的兜底）
    member_role: 'owner',        // 群身份：owner / admin / member
    bot: false,                  // 是不是机器人（挡自己发的消息时有用）
  },
  timestamp: '2026-01-01T00:00:00+08:00',
  qq_official: true,             // ← 框架补的标记
}
```

> **官方 `content` 里的 @ 标记，要全局剥，不能只剥开头。**
> 实测本机 `log/2026-10-13.log`，平台给的是**旧格式** `<@32位openid>`，而且位置不固定：
>
> ```text
> "<@4D8F...> 你好呀"                 ← 开头（多数情况）
> " <@4D8F...> 肥鱼能咬吗"            ← 开头，前面还多一个空格
> "那你看看这个是什么<@4D8F...> "     ← 句尾！只剥开头的正则会漏掉这条
> ```
>
> 漏掉的下场就是指令死活匹配不上、回声里带一坨 openid。所以正则要带 `/g`。
> 项目里既有的两处实现也都是全局的：`GF-plugin-mkai` 的 `RE_AT = /<@!?[A-Za-z0-9_]+>/g`、
> `src/core/log-format.ts` 的 `/<@([^>]*)>/g`。
>
> 新格式 `<qqbot-at-user id="openid" />` 实测**目前只在发送侧**见到（框架自己拼的），
> 接收侧还没出现过；一并兼容上，省得平台切过去就失效。

### 5.3 钩子怎么调、调几次

```text
一条事件进来
   ├─► plugin_onevent(ctx, event)     // 所有事件都调（含进群、按钮回调、动作回执）
   └─► plugin_onmessage(ctx, event)   // 只调「消息事件」
```

- **消息事件的判定**（与其它插件略有不同，双生插件这里帮你挡掉了噪音）：
  - OneBot：`event.post_type === 'message'`
  - 官方：`event.t` 里含 `MESSAGE` 或 `MSG_RECEIVE`
  - 动作回执（`post_type === 'action_result'`）**不会**进 `plugin_onmessage`。
- **同会话串行**：同一个群 / 同一个人发来的消息按顺序处理，跨会话才并发。
  官方被动回复依赖时序，所以别在插件里自己再并发。

## 六、发送侧：`actions.call` 自动分流

`ctx.actions.call` 是**同一个函数**，框架按当前连接类型决定往哪打：

| 连接类型 | 走哪套 | 例子 |
| --- | --- | --- |
| OneBot | OneBot 动作名 | `send_group_msg` / `send_private_msg` / `send_msg` / `get_login_info` / `set_group_ban` |
| QQ 官方 | 官方 REST 路径 | `/v2/groups/{group_openid}/messages` / `/v2/users/{user_openid}/messages` / `/v2/groups/{group_openid}/members/{openid}/mute` |

**参数格式各按各的来，框架不做转换**：

```js
// OneBot：动作名 + params
await ctx.actions.call('send_group_msg', { group_id: 888888, message: '你好' });

// 官方：路径 + body（被动回复必须带 msg_id）
await ctx.actions.call(`/v2/groups/${event.group_openid}/messages`, {
  content: '你好', msg_type: 0, msg_id: event.id, msg_seq: nextSeq(event.id),
});
```

> **官方侧 `msg_seq` 别写死 `1`。** 官方规定「相同 `msg_id` + `msg_seq` 重复发送会失败」
> （`GF-官方机器人/说明.md` 发送参数表），一条消息回第二次起就发不出去了。
> 做法是记住每条 `msg_id` 用到了第几号，示例里封装成 `nextSeq(msgId)`；
> 项目里实际在跑的 `sssx-plugin-book` 也是这么做的（还带 Map 上限裁剪，别让它无限涨）。

**群 / 单聊也要分路取 openid**，别一条 `a || b` 兜底：
`member_openid` 只在群内有效、`user_openid` 只在单聊有效，把 `member_openid`
塞进 `/v2/users/{id}/messages` 是打不通的。按 `event.t` 是否以 `C2C` 开头判断即可。

**鉴别诀窍**：官方的 action 一律以 `/` 开头（是 REST 路径），OneBot 的是下划线动作名。
所以一个通用的分路写法就是：

```js
const isOfficial = ctx.frameworkEnv.protocol === 'qq_official';
```

或者更省事——按 action 名自己判断：`String(action).startsWith('/')` 就是官方。

> 官方被动回复的时效与频控（每条 `msg_id` 最多 5 次、群聊 5 分钟内有效等）见
> `GF-官方机器人/说明.md` §八，双生插件照样受限。

## 七、数据、配置与日志目录

```text
data/123456/sssx-plugin-hello/          ← OneBot 账号的插件数据（QQ 号 123456）
data/1020xxxx/sssx-plugin-hello/        ← 官方账号的插件数据（AppID 1020xxxx）
```

- **两份数据是完全独立的**：同一个人在 QQ 群里签到，和在官方群里签到，积分不共用。
  想要共用就得你自己做跨账号存储（例如写到一个固定目录），框架不代劳。
- 配置同理：`ctx.configPath` 各指向自己那份 `config.json`。
- 插件设置界面（`plugin_config_ui` / `plugin_config_schema`）按**插件**展示，读的是**当前账号**那份配置。

## 八、后台页面：按原生方案来

**和单协议插件一模一样，没有任何双生专属写法**：

```js
// 初始化时注册
ctx.router.page({ path: 'admin', title: 'Hello 后台', module: 'webui/remote.js' });
```

或在 `package.json` 里声明 `webui`（经典 HTML）／ `webuiModule`（ESM 远程组件）。

后台入口的宿主路由按 **插件 ID + 账号** 生成，两个协议的账号各自有自己的后台地址，
互不影响。也就是说：**官方账号下打开的后台，看到的就是官方账号那份数据**。

## 九、最小可运行示例

见同目录 `sssx-plugin-hello/index.mjs`（整个文件夹丢进 `plugins/` 即可）。
它做的事：收到 `你好` / `ping` / `签到`，按来源协议各回各的话，并把积分写进自己的 `dataPath`。

核心骨架：

```js
async function plugin_init(ctx) {
  ctx.logger.info(`[hello] 启动，协议=${ctx.frameworkEnv?.protocol} 数据目录=${ctx.dataPath}`);
}

async function plugin_onmessage(ctx, event) {
  if (ctx.frameworkEnv?.protocol === 'qq_official') return onOfficial(ctx, event);
  return onOneBot(ctx, event);
}
```

## 十、发布到资源商城：填 `type: 双生`

GitHub 源 `index.json` 里每个插件对象的 `type` 决定商城卡片右上角显示哪个角标。
**双生插件要显式写 `双生`**，否则框架会把它归到「其他」，卡片上就看不到双生标签：

```jsonc
{
  "format": "kakake-plugins-v1",
  "plugins": [
    {
      "title": "Hello 双生",
      "plugin_id": "sssx-plugin-hello",
      "version": "1.0.0",
      "type": "双生",          // ← 关键。写 sssx / twin / 双生插件 也会被认成同一档
      "homepage": "https://github.com/you/sssx-plugin-hello",
      "download": "https://github.com/you/sssx-plugin-hello/releases/download/v1.0.0/plugin.zip"
    }
  ]
}
```

框架侧归一化规则（认不出的一律落「其他」）：

| 写的 `type` | 归一化结果 | 商城角标 |
| --- | --- | --- |
| `双生` / `双生插件` / `sssx` / `sssx-plugin` / `twin` | `双生` | 双生（品红） |
| `野生` | `野生` | 野生（橙） |
| `官方` | `官方` | 官方（天蓝） |
| `微信` | `微信` | 微信（翠绿） |
| 其它任何值 | `其他` | 其他（紫） |

商城顶栏的分类筛选按钮用的就是同一套归类，选「双生」只会留下上面那一行归到 `双生` 的资源。

## 十一、排错速查

| 现象 | 原因与处理 |
| --- | --- |
| 插件压根没被加载 | 目录名不是 `sssx-plugin-` 开头（大小写敏感），或 `plugins/` 放错层（应直接是 `plugins/sssx-plugin-xxx/index.mjs`） |
| 插件列表里看不到 | 总开关关了（`data/sssx-plugins.json` 里该键为 `false`），或没开连接子开关；去插件页刷新一次 |
| 只有一边有反应 | 另一条连接上没开这个插件的子开关；或在插件列表里切到那条连接单独开 |
| `ctx.frameworkEnv.protocol` 是 `undefined` | 该账号没有任何已启用连接，框架给不出协议；等连接连上再重载插件 |
| 官方侧发不出消息 | 被动回复缺 `msg_id`（= `event.id`），或超过 5 分钟时效；见 GF 手册 §八 |
| OneBot 侧发不出消息 | action 名写错了（应为 `send_group_msg` 这种，不是 REST 路径） |
| 群里收到消息但插件没进 `plugin_onmessage` | 官方要 `event.t` 含 `MESSAGE`；机器人没开「接收所有消息」时，只有被 @ 才会推 |
| 两份实例数据串了 | 不会串。检查是不是自己把数据写到了 `ctx.pluginPath`（会被覆盖）或固定目录 |
| 事件里既没有 `onebot` 也没有 `qq_official` | 不可能。出现了说明拿到的不是框架派发的事件（比如自己造的对象） |
| 官方群里指令死活匹配不上，回声里带一长串 openid | `content` 里的 @ 标记没剥干净。实测 @ 可能出现在**句尾**，只剥开头的正则会漏，要全局 `/g`（§5.2） |
| 官方侧第一条回复成功、第二条开始发不出 | `msg_seq` 写死成 `1` 了。同一 `msg_id` 的 seq 必须递增，否则官方判重复（§六） |
| 同一个人在不同官方群里积分各算一份 | 正常现象。`member_openid` 是按群变的，拿它当主键就会这样；要跨群打通得自己做一层映射 |
